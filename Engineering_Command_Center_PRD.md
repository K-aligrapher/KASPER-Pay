# Engineering Command Center
## Product Requirements Document (PRD)

**Version:** 1.0  
**Status:** Draft — implementation-ready baseline  
**Project type:** Local-first AI engineering productivity platform  
**Primary stack:** C# / .NET, Ollama, React + TypeScript, SQLite  
**Cost target:** $0 for local development and inference, excluding any provider plan requirements or optional hardware  
**Combines:** Personal Engineering Command Center + Local AI Agent Runtime

---

## 1. Executive Summary

Engineering Command Center (ECC) is a local-first platform that unifies engineering context and safely orchestrates AI-assisted workflows across Slack, Notion, GitHub, and Ollama.

The product has two integrated capabilities:

1. **Engineering Command Center:** a unified interface to ask questions across connected engineering tools, review project context, summarize discussions, track pull requests, and turn decisions into proposed tasks.
2. **Local AI Agent Runtime:** a reusable, observable execution engine that discovers and invokes approved tools, manages multi-step workflows, persists state, handles failures, and enforces approval and permission policies.

ECC is not intended to be an unrestricted autonomous agent. The LLM proposes structured plans; deterministic application code validates, authorizes, and executes them. External write actions require explicit approval by default.

The first release should run on a developer's Windows laptop, use Ollama for local inference, and avoid paid AI APIs or cloud-hosted application infrastructure.

## 2. Problem Statement

Engineering work is distributed across chat, documentation, source control, and local development environments. Developers repeatedly switch applications to answer questions, recover decisions, create follow-up tasks, and understand pull requests.

Generic chat interfaces do not reliably preserve workflow state or enforce execution permissions. Direct API integrations can become tightly coupled to one provider, while unconstrained agents introduce risks such as duplicate actions, hallucinated tool calls, lost progress, and unauthorized writes.

ECC addresses these problems with a unified interface and a reusable workflow runtime that is:
- Context-aware across connected engineering tools.
- Local-first for model inference and core application state.
- Modular and extensible through adapters and optional MCP integration.
- Durable, auditable, and testable.
- Approval-gated for actions that change external systems.

## 3. Goals

### 3.1 Product goals
- Provide one interface for common engineering context and workflow tasks.
- Connect Slack, Notion, GitHub, and a local Ollama model.
- Summarize selected discussions and extract decisions/action items with source references.
- Generate Notion task drafts from engineering discussions.
- Retrieve GitHub repository, issue, and pull-request context.
- Provide a reusable tool-calling runtime with bounded execution and explicit permissions.
- Persist workflow state, approval decisions, tool results, and audit events.
- Make errors and agent behavior understandable through execution traces.

### 3.2 Engineering goals
- Use a modular monolith before considering microservices.
- Separate domain rules, application use cases, infrastructure integrations, and HTTP/UI concerns.
- Make workflows resumable after application restart.
- Validate all model-generated structured output.
- Test workflow logic independently from live provider APIs.
- Keep secrets out of source control and logs.
- Support local development without paid LLM APIs.

## 4. Non-Goals

The first release will not:
- Replace Slack, Notion, or GitHub.
- Train or fine-tune an LLM.
- Allow arbitrary shell, PowerShell, SQL, or Kubernetes commands generated by a model.
- Merge pull requests, deploy applications, or execute destructive operations autonomously.
- Guarantee perfect semantic understanding of every conversation or repository.
- Require Kubernetes, Kafka, Redis, or a hosted vector database.
- Build a general-purpose multi-agent society or unrestricted self-modifying agent.
- Promise zero cost for provider access; provider plans, API limits, workspace permissions, and network access still apply.
- Ingest every message or repository by default. Access should be scoped to explicitly authorized resources.

## 5. Target Users and Primary Use Cases

### Primary user
A software engineer or student developer working across multiple repositories, team discussions, and project documents who wants to automate repetitive engineering coordination without surrendering control of external actions.

### Core use cases
1. Ask a question about a selected Slack discussion, Notion page, or GitHub pull request.
2. Summarize a discussion and extract decisions, action items, owners when explicitly stated, and unresolved questions.
3. Draft a Notion task from a discussion, inspect the draft, approve it, and create it.
4. Review a pull request's metadata and changed-file context.
5. Run a predefined multi-step workflow through registered tools.
6. Inspect each workflow's plan, execution steps, inputs/outputs, errors, retries, and approval decisions.
7. Register a new tool or provider adapter without rewriting the orchestration core.

## 6. Product Principles

- **Local-first:** use Ollama for inference and local storage for application state by default.
- **Human control:** model output is a proposal, not authorization.
- **Least privilege:** grant the smallest practical provider scopes.
- **Explicit execution:** only registered tools can be called; no arbitrary code execution.
- **Traceability:** every workflow and tool invocation has a stable identifier and recorded outcome.
- **Resilience:** workflow state must survive restarts and recover from transient failures.
- **Provider isolation:** provider-specific details remain inside adapters.
- **Incremental complexity:** begin with direct REST adapters and a single-process worker; add MCP and advanced infrastructure when justified.

## 8. Functional Requirements

Priority definitions: **P0** = required for first usable release; **P1** = important follow-up; **P2** = optional enhancement.

### 8.1 Integrations and configuration
- **FR-001 (P0):** The system shall support configurable Ollama base URL and model name.
- **FR-002 (P1):** The system shall provide connection diagnostics for each configured provider.
- **FR-003 (P1):** The system shall support GitHub, Notion, and Slack through isolated adapters.
- **FR-004 (P1):** The system shall allow the operator to enable/disable each integration.
- **FR-005 (P1):** The system shall scope access to explicitly configured workspaces, repositories, channels, pages, or data sources.
- **FR-006 (P1):** The system shall support MCP tools through an adapter layer without making MCP mandatory for every integration.
- **FR-007 (P0):** Credentials shall be loaded from development secrets, environment variables, or a suitable local secret store, never committed to source control.

### 8.2 AI interaction and planning
- **FR-010 (P0):** The system shall accept a user prompt and return a response from the configured Ollama model.
- **FR-011 (P0):** The runtime shall provide the model only with tools available to the current user and workflow.
- **FR-012 (P0):** The model shall produce a structured plan for tool-using workflows.
- **FR-013 (P0):** The system shall validate model output against typed schemas and reject malformed or unsupported actions.
- **FR-014 (P1):** The system shall attach source identifiers and URLs to retrieved context where available.
- **FR-015 (P1):** The system shall distinguish observed facts, model-generated interpretations, and proposed actions in the UI and stored results.
- **FR-016 (P1):** The system shall support bounded model/tool iterations and a configurable maximum workflow step count.
- **FR-017 (P2):** The system may support semantic retrieval over authorized content, with deletion and refresh behavior defined before indexing is enabled.

### 8.3 Tool registry and execution runtime
- **FR-020 (P0):** Every callable tool shall have a stable identifier, description, typed input schema, permission classification, and implementation.
- **FR-021 (P0):** Only registered tools shall be invocable.
- **FR-022 (P0):** Every invocation shall be validated before execution.
- **FR-023 (P0):** Tool execution shall support cancellation and timeouts.
- **FR-024 (P0):** Retries shall be bounded and applied only to classified retryable errors.
- **FR-025 (P0):** Write operations shall support idempotency or duplicate detection where feasible.
- **FR-026 (P0):** The runtime shall persist workflow state and step outcomes.
- **FR-027 (P1):** A workflow interrupted by a restart shall resume safely or enter a clear recoverable/failed state.
- **FR-028 (P1):** The runtime shall record tool inputs/outputs with sensitive fields redacted according to policy.
- **FR-029 (P1):** The runtime shall support tool health and availability status.
- **FR-030 (P1):** The runtime shall support an MCP adapter with server allowlisting and per-tool authorization.

### 8.4 Workflow lifecycle and approvals
- **FR-040 (P0):** Workflow states shall include `Pending`, `Running`, `WaitingForApproval`, `Succeeded`, `Failed`, and `Cancelled`.
- **FR-041 (P0):** Each workflow shall have a stable ID, creator/requester, timestamps, status, and execution history.
- **FR-042 (P0):** The system shall require explicit approval before external write actions by default.
- **FR-043 (P0):** Approval shall be bound to a specific action payload and target; material changes invalidate the approval.
- **FR-044 (P0):** Approval requests shall support approve and reject outcomes and record the decision-maker and time.
- **FR-045 (P0):** The system shall not treat a model-generated statement as user approval.
- **FR-046 (P1):** The system shall support cancellation of workflows and safe handling of in-flight steps.
- **FR-047 (P1):** The system shall expose workflow status and the reason for waiting or failure.

### 8.5 Initial end-to-end workflow
- **FR-050 (P1):** A user shall select or provide a permitted Slack discussion and/or GitHub context.
- **FR-051 (P1):** The system shall gather context through authorized adapters.
- **FR-052 (P1):** Ollama shall generate structured decision and action-item candidates.
- **FR-053 (P1):** Each candidate shall include source references where available and shall not invent an owner when none is stated.
- **FR-054 (P1):** The system shall generate a Notion task preview without immediately writing to Notion.
- **FR-055 (P1):** A user shall review and approve/reject the proposed task.
- **FR-056 (P1):** After approval, the system shall create the task and store the external ID/URL and execution result.
- **FR-057 (P1):** Duplicate task creation shall be prevented where feasible using an idempotency key or stored execution record.
- **FR-058 (P1):** The workflow shall be inspectable from start to finish in the dashboard/API.

## 9. Non-Functional Requirements

### Security and privacy
- NFR-001: Bind local development services to loopback by default.
- NFR-002: Do not expose Ollama, the API, or the dashboard to a public network without deliberate authentication and network configuration.
- NFR-003: Never log access tokens, authorization headers, passwords, or secret values.
- NFR-004: Apply least-privilege provider permissions and allowlist permitted resources.
- NFR-005: Treat Slack messages, Notion pages, GitHub content, and MCP tool output as untrusted data. Content must not override system policies or authorize actions.
- NFR-006: Validate all inputs, enforce request size limits, and use parameterized database operations.
- NFR-007: Approval must be checked server-side immediately before an external write.
- NFR-008: Store only the context needed for the workflow; define retention and deletion behavior.
- NFR-009: Verify provider webhook signatures, timestamps, and replay protections before processing incoming events.
- NFR-010: External tool servers must be explicitly configured and trusted; do not auto-run arbitrary MCP servers discovered from content.

### Reliability
- NFR-020: Persist workflow state before beginning external side effects.
- NFR-021: External API calls shall have timeouts and cancellation support.
- NFR-022: Retries shall use bounded exponential backoff with jitter when appropriate.
- NFR-023: The system shall distinguish transient, permanent, authorization, validation, and rate-limit failures.
- NFR-024: Workflow steps shall be designed for idempotent replay or explicit manual recovery.
- NFR-025: Database migrations shall be versioned and tested.

### Observability
- NFR-030: Use structured logs with correlation, workflow, and step IDs.
- NFR-031: Record workflow start/end, status transitions, tool name, duration, retry count, and error category.
- NFR-032: Keep model prompts and provider content out of routine logs by default; detailed traces must be opt-in and redacted.
- NFR-033: Expose local health/readiness endpoints without leaking credentials or private provider data.

### Performance and resource use
- NFR-040: The UI shall remain responsive while model inference or external calls run.
- NFR-041: Long-running workflows shall execute outside the HTTP request lifetime.
- NFR-042: Model inference and tool execution limits shall be configurable.
- NFR-043: Initial implementation shall support a single developer and low-volume personal workflows; scale targets shall be defined using measured workloads rather than guessed.
- NFR-044: Local inference shall be configurable for smaller models and bounded context lengths to fit available hardware.

### Maintainability
- NFR-050: Domain and application logic shall be testable without live external services.
- NFR-051: Provider-specific code shall be isolated behind interfaces.
- NFR-052: Public API contracts shall use request/response DTOs and validation.
- NFR-053: Configuration shall be environment-specific and documented.
- NFR-054: The repository shall include setup, troubleshooting, architecture, and security documentation.

## 12. Workflow State Machine

Allowed primary transitions:

```text
Pending -> Running
Running -> WaitingForApproval
WaitingForApproval -> Running       (approved; revalidate action)
WaitingForApproval -> Cancelled     (rejected/cancelled)
Running -> Succeeded
Running -> Failed
Running -> Cancelled
Failed -> Pending                   (explicit retry/recovery, when safe)
```

Implementation rules:
- Persist each transition transactionally.
- Never mark a workflow successful until all required steps and side effects are confirmed.
- Before an external write, re-check the action hash, approval status, permission policy, target, and idempotency key.
- If the provider times out after a write request, reconcile the external state before retrying; a timeout does not prove that the write failed.
- Keep human approval separate from LLM planning.

## 14. Tool Contract

Every tool should declare:
- Stable tool ID and version.
- Human-readable description.
- Typed input schema.
- Read/write classification.
- Required permission.
- Allowed targets/resource scope.
- Timeout and retry policy.
- Idempotency behavior.
- Data sensitivity classification.
- Whether approval is required.

Illustrative tools:
- `github.list_pull_requests` — read.
- `github.get_pull_request` — read.
- `notion.search_pages` — read.
- `notion.create_task` — write; approval required.
- `slack.get_thread` — read.
- `slack.draft_message` — draft-only initially; sending would require approval.

Do not provide a generic `execute_shell` tool to the model in the initial release.

## 15. AI Planning Contract

The model should return a constrained plan, for example:

```json
{
  "summary": "Create a task from a confirmed engineering decision",
  "steps": [
    {
      "toolId": "slack.get_thread",
      "purpose": "Retrieve the selected discussion",
      "input": {
        "channelId": "configured-channel-id",
        "threadTs": "selected-thread-id"
      }
    },
    {
      "toolId": "notion.create_task",
      "purpose": "Create an approved follow-up task",
      "requiresApproval": true,
      "input": {
        "title": "Draft title",
        "description": "Draft description"
      }
    }
  ]
}
```

This is illustrative only; provider IDs must come from authorized application context, not model invention. The server must verify that each tool exists, each argument matches its schema, the caller can access the target, and the plan stays within step and execution limits. The model cannot set approval state.

## 16. Security and Threat Model

### Main threats
- Prompt injection embedded in Slack, Notion, GitHub, or MCP output.
- A model hallucinating tool names, resource IDs, or arguments.
- Stolen or overprivileged provider tokens.
- Duplicate external writes after retries or ambiguous timeouts.
- Unauthorized access to private engineering content.
- Local API access by another process or user on the machine/network.
- Sensitive data exposure through logs, traces, or vector indexes.
- Malicious or compromised MCP servers.

### Mitigations
- Treat retrieved content as untrusted data and keep instructions separate from data.
- Use allowlisted tools and server-side schema validation.
- Enforce authorization and resource scope outside the model.
- Require approval for external writes and bind approval to a canonical action hash.
- Use minimum provider scopes and rotate/revoke credentials when needed.
- Bind local endpoints to loopback by default; add authentication for any broader exposure.
- Redact secrets and minimize retained provider content.
- Allowlist MCP servers, inspect their tools, and grant per-tool permissions.
- Verify webhooks and prevent replay before enabling inbound triggers.
- Use test accounts or sandbox workspaces for integration development.

## 17. Testing Strategy

### Unit tests
- Workflow state transitions.
- Plan and tool schema validation.
- Permission-policy evaluation.
- Approval invalidation when payload changes.
- Idempotency-key generation and duplicate detection.
- Retry classification and step-count limits.
- Redaction and audit event generation.

### Integration tests
- Ollama adapter against a local test model or a deterministic HTTP stub.
- SQLite persistence and migrations.
- Provider adapters against mocked HTTP responses.
- Timeouts, rate limits, malformed JSON, and authorization errors.
- Workflow recovery after simulated restart.
- Approval required before external writes.

### End-to-end tests
- Create a workflow from a user prompt.
- Retrieve mocked Slack/GitHub context.
- Generate a task draft.
- Confirm the system pauses for approval.
- Approve and verify exactly one mocked Notion task creation.
- Reject an action and verify no write occurs.
- Simulate a provider timeout after a write and verify safe reconciliation.

Do not make the test suite dependent on live Slack, Notion, or GitHub accounts for ordinary CI runs.

## 18. Acceptance Criteria for the First Useful Release

The first useful release is accepted when:

1. The application runs locally on Windows with documented setup steps.
2. Ollama can be called through a typed .NET adapter.
3. A user can create and inspect a persisted workflow.
4. The runtime uses only registered, schema-validated tools.
5. Workflow steps and status transitions survive application restart.
6. Tool timeouts and failures are recorded and handled without unbounded retries.
7. A write action pauses for explicit user approval.
8. Approval is invalidated if the proposed action payload or target changes.
9. Secrets are not committed or written to routine logs.
10. Unit and integration tests cover approval, failure, and duplicate-action scenarios.
11. At least one real provider integration can retrieve authorized data.
12. The Notion task workflow can create exactly one task after approval in a test workspace.

## 21. Risks and Open Questions

- **Provider plan/permissions:** confirm which Slack and Notion API capabilities are available for the target workspace and account.
- **Local model quality:** small local models may produce malformed plans or miss subtle context; validation and evaluation are mandatory.
- **Context limits:** large Slack threads and pull requests need bounded retrieval and summarization.
- **Duplicate writes:** provider timeouts can make the result of a write ambiguous; implement reconciliation before retrying.
- **MCP trust:** an MCP server can expose powerful tools; each server and tool requires explicit review and permissions.
- **Privacy:** local inference does not automatically make third-party data collection or storage safe. Minimize retained content and protect local state.
- **Desktop resource use:** keep model size and context length configurable, and monitor temperatures and memory use on the development laptop.
- **Authentication model:** initial use is a single local operator; multi-user/team access is outside the first release and requires a stronger identity and authorization model.

## 22. Definition of Done

A feature is complete only when:
- The behavior and failure cases are documented.
- Inputs and model outputs are validated.
- Permissions are enforced server-side.
- External side effects are approval-gated where required.
- Workflow state and audit events are persisted.
- Unit and integration tests pass.
- Logs redact secrets and avoid unnecessary content retention.
- Setup and recovery steps are documented.
- The feature works without paid LLM APIs.
